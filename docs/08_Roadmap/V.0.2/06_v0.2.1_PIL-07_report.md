# PIL-07 — Caddy `X-Forwarded-For` ба Supabase Auth-ийн хязгаар (тайлан)

> 2026-10-11 · Төлөв: **засав (#15)** — таны шийдвэр: Caddy `trusted_proxies` + бүртгэлийн түгжээ (`password_verification_attempt` hook, арга 1). Staging-д `pilot.ps1 auth-test` хүлээгдэж байна

## Зам

Интернэт → Tailscale Funnel → Caddy `127.0.0.1:8088` → Kong `127.0.0.1:55321` → GoTrue (`/auth/v1/token`)

## Олдвор

| # | Давхарга | Үр дүн | Хэрхэн шалгасан |
|---|---|---|---|
| 1 | Tailscale Funnel | Хэрэглэгчийн бодит IP-г `X-Forwarded-For`-д тавьдаг | эх код `ipn/ipnlocal/serve.go` `addProxyForwardedHeaders` |
| 2 | **Caddy (одоогийн)** | Ирсэн `X-Forwarded-For`-ийг **хаяж**, `127.0.0.1` болгоно → бүх хэрэглэгч нэг IP | Caddy 2.8.4 + одоогийн Caddyfile + echo upstream: `XFF: 203.0.113.7` → upstream `127.0.0.1` |
| 3 | Caddy + `trusted_proxies 127.0.0.1` | `203.0.113.7, 127.0.0.1` → бодит IP эхэнд | ижил тест, санал болгох засвар |
| 4 | GoTrue | IP-ээр хязгаарлах нь **зөвхөн `GOTRUE_RATE_LIMIT_HEADER` тохируулсан үед**; хоосон бол `/token`-д IP хязгаар **огт үйлчлэхгүй** | эх код `internal/api/middleware.go` `performRateLimitingWithHeader` |
| 5 | Supabase CLI | `GOTRUE_RATE_LIMIT_HEADER`-ийг тохируулдаггүй | эх код `gotrue.service.ts` (env жагсаалт) |

**Дүгнэлт:** одоо пилотод `config.toml`-ийн `sign_in_sign_ups` / `token_refresh` хязгаар нэвтрэлтэд **үйлчлэхгүй байх магадлал өндөр** (нууц үг таах оролдлогыг IP-ээр хязгаарлахгүй). Зөвхөн Caddy-г засах нь хангалтгүй — GoTrue-д header-ийг заах ёстой. Kong-ийн XFF зан төлөвийг бодитоор шалгаагүй (Kong ирсэн XFF-ийн ард өөрийн peer IP-г нэмдэг гэж үздэг).

## Staging дээр батлах (5 мин)

```powershell
# 130 удаа буруу нууц үг → одоо 429 гарахгүй бол олдвор #4 батлагдана
1..130 | % { (Invoke-WebRequest -Method Post -Uri "http://127.0.0.1:8089/auth/v1/token?grant_type=password" -Headers @{apikey=$env:ANON} -ContentType 'application/json' -Body '{"email":"nobody@example.com","password":"x"}' -SkipHttpErrorCheck).StatusCode } | Group-Object | ft Count,Name
```

## Санал болгох засвар (батлуулсны дараа)

1. `deploy/pilot/Caddyfile` — global block:
   ```
   servers {
   	trusted_proxies static 127.0.0.1/32 ::1/128
   	client_ip_headers X-Forwarded-For
   }
   ```
   (Caddy зөвхөн localhost-оос ирсэн XFF-д итгэнэ — Caddy `127.0.0.1`-д bind хийсэн тул гаднаас хуурамч XFF ирэхгүй.)
2. GoTrue-д `GOTRUE_RATE_LIMIT_HEADER=X-Forwarded-For` — Supabase CLI-аар хэрхэн дамжуулахыг (config.toml / docker override) staging дээр шалгах шаардлагатай.
3. Staging дээр дээрх тестээр: нэг IP → 429, өөр `X-Forwarded-For` → тусдаа хязгаар.

## Хэрэгжүүлэлт (#15)

- Caddyfile: `servers { trusted_proxies static 127.0.0.1/32 ::1/128; client_ip_headers X-Forwarded-For }` — Caddy 2.8.4: `XFF: 203.0.113.7` → upstream `203.0.113.7, 127.0.0.1`.
- `supabase/migrations/20261012006_auth_password_guard.sql`: `auth_guard.password_failures` + `auth_guard.hook_password_verification_attempt`. 15 мин-д 5 буруу → 15 мин түгжинэ. Hook-ийн `error.http_code = 429` → GoTrue `429` (`decision: reject` бол 400 байх байсан).
- `deploy/{pilot,staging}/supabase/config.toml`: `[auth.hook.password_verification_attempt]`.
- `pilot.ps1`: `auth-test` (staging), `unlock`, `init` — config.toml өөрчлөгдвөл migration-ы дараа Supabase дахин асаана (эс бөгөөс upgrade-ийн дараа hook идэвхжихгүй).
- Баталгаа: бодит GoTrue v2.178 + PG16 (CHANGELOG [v0.2.1] "Тест"). Хязгаарлалт: IP-ээр биш бүртгэлээр — олон бүртгэлийг нэг IP-ээс оролдохыг хаахгүй; бусдын бүртгэлийг 15 мин түгжиж болно (`unlock`).
