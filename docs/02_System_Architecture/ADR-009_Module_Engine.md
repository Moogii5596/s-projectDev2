# ADR-009 — Цөм = модуль ажиллуулах хөдөлгүүр; модуль = зөвхөн бизнесийн логик

> **Шийдвэр (хэрэглэгч, 2026-11-07):** нийтлэг боломжийг давтаж хийхгүй — цөмд нэг удаа, модуль бүр ашиглана. Цөм нь ямар ч модуль суулгах хөдөлгүүр; модуль зөвхөн бизнесийн логиктойгоо ирж сууна. Агентын дүрэм → `AGENTS.md` §1б. Хуваарь → [[11_v0.2_completion_master_plan]].

## 1. Яагаад
- S Project бүх салбарт (кемп, HR, хүргэлт, ресторан, зочид буудал…) зориулагдсан ([[PRD-06_Vision_Business_Model]]). Салбар бүр шинэ модуль — нийтлэг боломжийг модуль бүрт дахин бичвэл хурд, чанар хоёулаа унана.
- Кодын анализ (2026-11-07): цөм ба HR, Feed нь **Кемп модулийн** `camp/common` (эрх, transaction, алдаа, огноо, audit)-оос хамаардаг; frontend-ийн суурь UI (`modules/camp/components/ui.tsx`, hook, lib)-ийг HR, Feed, Settings ашигладаг; цөмийн байгууллага Кемпийн `camp_service_types`-д холбогдсон. Хамаарал урвуу — Кемпийг унтраах, шинэ модуль нэмэх бүрт эрсдэл.

## 2. Шийдвэр

### 2.1 Хамаарлын дүрэм (CI-д eslint-ээр шалгана)
1. **Цөм модулиас хамаарахгүй** (`core` → `modules/*` import ✖, цөмийн хүснэгт модулийн хүснэгтэд FK ✖).
2. **Модуль зөвхөн цөмөөс** импортлоно. Модуль хооронд шууд import ✖.
3. Модуль хоорондын хэрэгцээ (жнь Кемп ← HR-ийн ажилтан) → **цөмд тодорхойлсон интерфейс (port, DI token)**, хангагч модуль бүртгэнэ; нэг transaction-д дуудаж болно ([[ARCH-00_System_Overview]] §5-3). Мэдэгдэл / интеграц → outbox event.
4. Модулийн хүснэгт өөрийн угтвартай (`camp_*`, `hr_*`, `feed_*`); цөмийнх `core_*`.

### 2.2 Модулийн manifest (нэг гэрээ)
Модуль бүр backend + frontend-д **нэг manifest**-ээр бүртгэгдэнэ; цөм түүнийг уншиж ажиллуулна — цөмийн кодыг өөрчлөхгүй:

| Талбар | Цөмийн хэрэглэгч |
|---|---|
| `id`, хамаарал (`requires`) | Модулийн registry, runtime асаах/унтраах (SYS-02) |
| Эрхийн код (`hr.*`, `camp.*`) | ADR-007 эрхийн каталог |
| Цэс, route (lazy), нүүрний виджет | Апп-ын хүрээ (UX-01), хяналтын самбар |
| Тохиргооны хэсэг | `/settings` registry (SYS-01) |
| i18n namespace, нэр томьёо (`term.*`) | Орчуулга v2 (I18N-03) |
| Audit-ийн entity | Audit (`core_audit_log`) |
| Батлалтын төрөл + төлөвийн callback | Батлах хөдөлгүүр (WF-06) |
| Мэдэгдлийн төрөл | Мэдэгдэл (NTF-01) |
| Хавсралтын төрөл (PII эсэх) | Файл (FILE-01) |
| Импорт / экспортын тодорхойлолт | Импорт/экспорт (Excel, preview → батлах) |
| Тайлангийн dataset | Тайлангийн хөдөлгүүр |
| Feed-д холбогдох объектын төрөл + эрхийн шалгалт | Feed холбоос (`feed_links`) |
| Хуваарьт ажил (cron) | Scheduler |
| Дугаарлалтын загвар | Дугаарлалт |

## 3. Үр дагавар
- v0.2.4 = цөмийг бүрэн болгох (дээрх 🔄 бүгд зөөгдөж, 📋-ийн HR / Кемпэд хэрэгтэй нь хийгдэнэ). Дараагийн хувилбар бүр өөрт хэрэгтэй цөмийн боломжийг нэмнэ; цөм ба модулийн ажил зэрэг явна — модулийн ашиглах цөмийн интерфейсийг эхэлж тогтооно.
- Одоогийн Кемп, HR, Feed модулийг цөмийн боломж руу шилжүүлнэ (давхардсан кодыг устгана). Шилжилт бүрт өмнөх API, эрх, өгөгдөл хэвээр (A = B).
- Шинэ салбарын модуль (жнь ресторан) = зөвхөн өөрийн хүснэгт, дүрэм, дэлгэц + manifest.
- Зөрчил (цөм → модуль import, модуль ↔ модуль import) CI-д унана.
