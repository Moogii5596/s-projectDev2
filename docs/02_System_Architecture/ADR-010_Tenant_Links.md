# ADR-010 — Байгууллага хоорондын холболт (tenant link, B2B)

> 2026-11-10 · Төлөв: **📝 Санал (Draft)** — хэрэглэгч батлаагүй; §7-ийн асуултыг хариулсны дараа «Active» болно.
> Холбоотой: [[ADR-001_Tenant_Isolation]] (RLS, dedicated) · [[ADR-005_Org_Connectivity_Domains]] (домэйн, байрлал) · [[ADR-009_Module_Engine]] (outbox, интерфейс) · [[ADR-003_Users_Login_Permissions]] · [[PRD-06_Vision_Business_Model]] §6 · [[00_backlog_and_tech_debt]] §1г (LINK-*)

## 1. Нөхцөл
- Нэвтрэх стратеги ([[PRD-06_Vision_Business_Model]] §6.1): Sino дээрх катерингийн ажил (хоолны тоо, цэс, гомдол, нэхэмжлэх)-ыг **катерингийн компани өөрийн tenant-аас** хийнэ. Катеринг өөрийн хүнд асуудлаа (тулгалт, түүхий эд, өртөг, ажилтан) мөн системээр шийдэж болохыг өөрөө анзаарна — гүйцэтгэгч бүр дараагийн захиалагчаа дагуулж ирнэ.
- Одоо: tenant бүр RLS-ээр **хатуу тусгаарлагдсан**; Sino нь **dedicated** горимд өөрийн PC дээр ([[ADR-002_Hosting]]). Катерингийн компани Sino tenant дотор `camp_organizations`-ийн нэг мөр, хэрэглэгчид нь Sino-гийн хэрэглэгч (катеринг админ роль).
- [[ADR-005_Org_Connectivity_Domains]] зөвхөн домэйн, сүлжээг шийддэг — tenant хооронд өгөгдөл солилцох загвар байхгүй.

## 2. Шийдвэр (санал)

### 2.1 Катерингийн tenant хаана
- Катеринг = **тусдаа tenant, shared сервер дээр** (ADR-005 §2.2-ийн 3-р төрөл, `<slug>.gobiverse.website`).
- Sino-гийн серверт **байрлуулахгүй**: нийлүүлэгчийн өгөгдөл (бусад үйлчлүүлэгчийнх нь хамт) захиалагчийн машинд хадгалагдах нь хоёр талд хүлээн зөвшөөрөгдөхгүй.
- Иймээс холболт нь **instance хооронд** ажиллах ёстой; нэг instance дээрх хоёр tenant ч яг ижил замаар холбогдоно (тусгай «shortcut» ✖).

### 2.2 Холболт = гэрээ, хуваалцсан мөр биш
- Хоёр tenant нэг мөрийг хуваалцахгүй, хоорондоо DB-ээр холбогдохгүй — RLS тусгаарлалт хэвээр.
- Tenant бүрт `core_tenant_links` (өөрийн талын бичлэг): эсрэг талын tenant/instance, төлөв (`INVITED → ACTIVE → SUSPENDED → REVOKED`), өөрийн `camp_organizations` (→ цөмийн байгууллага, CORE-02)-ийн аль мөртэй тохирох, **хүрээ (scope)**-ийн жагсаалт.
- Холбох урсгал: захиалагч (Sino) урилга үүсгэнэ (нэг удаагийн код) → гүйцэтгэгч өөрийн tenant-д хүлээн авна → хоёр талын OWNER/ADMIN хүрээг батална. Хүрээ нэмэх/хасах бүр хоёр талын батлалттай, audit-тай.
- Солилцоо: **outbox event → гарын үсэгтэй HTTPS** (tenant link бүрт тусдаа түлхүүр, rotate боломжтой). Хүлээн авагч тал өөрийн tenant-д хуулбар хадгална (idempotent, `event_id`-ээр давхардалгүй). Холбоо тасарвал outbox дахин оролдоно — dedicated/интернэт тасалдаг кемпэд тохирно.
- Цөмийн боломж ([[ADR-009_Module_Engine]] §2.3): «Tenant link» — модуль manifest-ээр **хуваалцах объектын төрөл + scope**-оо бүртгэнэ; модуль өөрөө сүлжээ, түлхүүр мэдэхгүй.

### 2.3 Эхний хүрээ (кемпийн катеринг)
| Scope | Эх сурвалж (эзэн) | Нөгөө тал | Агуулга |
|---|---|---|---|
| `meal.counts` | Захиалагч (Sino) | Катеринг уншина, **баталгаажуулна** | Өдөр × хоолны цаг × хоолны байршил × (хэлтэс)-ийн тоо, зочин/нэмэлт, өөрчлөлт |
| `meal.menu` | Катеринг | Захиалагч уншина (Feed-д өнөөдрийн цэс) | CMP-03 |
| `meal.complaints` | Захиалагч (ажилтны гомдол) | Катеринг хариу, «шийдсэн» | CMP-04 / FEED-06; зураг хавсралт |
| `contract.prices` | **Хоёр тал** (хувилбартай, хоёулаа батална) | — | v0.2.3 Блок 6б-ийн гэрээ, үнэ, ханш |
| `billing.reconciliation` | **Хоёр тал** | — | Сарын хоолны тооны тулгалт → батлагдсан тоо → нэхэмжлэх |

- **PII ✖:** хүрээ анхдагчаар зөвхөн **нэгтгэсэн тоо**. Ажилтны нэр, утас, имэйл (PIL-14) дамжихгүй. Нэрсийн жагсаалт (жнь тусгай хоолтой ажилтан) хэрэгтэй бол тусдаа scope, захиалагчийн тодорхой зөвшөөрөл, хандалтын лог.
- **Сарын тулгалт** — хоёр тал нэг тоог харж, зөрүүг мөр бүрээр тэмдэглэж, хоёулаа батална; батлагдсан хувилбар түгжигдэнэ. Энэ нь катерингийн гол «толгойн өвчин» тул эхний үнэ цэн.

### 2.4 Хэрэглэгчид
- Катерингийн ажилтан **катерингийн tenant-ын хэрэглэгч** болно. Sino tenant дахь одоогийн катеринг админ хэрэглэгчийг холболт идэвхжсэний дараа шилжүүлнэ (LINK-07): хоёр талд давхар нэвтрэх хугацаа → Sino талд эрхийг цуцлах. Өгөгдөл устгах биш — `AGENTS.md` §4 эрсдэлтэй үйлдэл.
- Нэг хүн олон байгууллагад (хувь хүний аккаунт) — **энэ ADR-ийн хүрээнд биш**; холболт нь байгууллага ↔ байгууллага. Нийтийн сүлжээнд хэрэгтэй хувь хүний identity → ID-01 (тусдаа ADR).

## 3. Хасагдсан хувилбарууд
| Хувилбар | Яагаад ✖ |
|---|---|
| Катерингийн хэрэглэгчийг Sino tenant-д үргэлжлүүлэн ажиллуулах | Катерингт өөрийн орон зай алга → өөр үйлчлүүлэгчээ авчрах шалтгаангүй; стратегийн гол санаа алдагдана |
| Хоёр tenant-д хуваалцсан хүснэгт (`tenant_id` хоёр, RLS-ийн үл хамаарал) | ADR-001 тусгаарлалтыг эвдэнэ; dedicated instance хооронд ажиллахгүй |
| Катерингийг Sino-гийн серверт нэмэлт tenant болгох | Нийлүүлэгчийн өгөгдөл захиалагчийн машинд; нөөцлөлт, хариуцлага холилдоно |

## 4. Үр дагавар
- (+) RLS, dedicated загвар хэвээр; нэг instance / олон instance нэг замаар.
- (+) Холболт бүр хүрээтэй, audit-тай, цуцлах боломжтой — байгууллагуудын итгэл.
- (−) Eventual consistency: тоо хэдэн секунд–минут хоцорч болно; тулгалт нь **батлагдсан хувилбар** дээр хийгдэнэ.
- (−) Instance хоорондын түлхүүр, retry, хувилбарын нийцэл (event schema version) — нэмэлт ажил.
- (−) Shared сервер хэрэгтэй (ADR-002 одоо зөвхөн пилот PC) — хостингийн шийдлийг өргөтгөнө.

## 6. Аюулгүй байдал
- Link бүрт тусдаа түлхүүр; хүлээн авахад гарын үсэг, timestamp (replay ✖), scope шалгана.
- Хүлээн авсан өгөгдөл хүлээн авагчийн tenant-д RLS-тэй хадгалагдана; эх тал цуцалбал (`REVOKED`) шинэ event зогсоно, хуучин хуулбарыг хадгалах хугацаа гэрээгээр.
- Cloudflare-аар TLS тайлагддаг (ADR-005 §3) — B2B өгөгдөлд хүлээн зөвшөөрөгдөх эсэхийг захиалагчаас асууна.

- [ ] Хоолны тооны эх сурвалж Sino байх уу, эсвэл хоёр тал өдөр бүр батлах уу (санал: Sino эзэн, катеринг баталгаажуулна, сард хоёулаа батална)?
