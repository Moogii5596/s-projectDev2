# ADR-003 — Ажилтан ↔ Хэрэглэгч, нэвтрэлт, эрхийн загвар

> Төлөв: **Батлагдсан (шийдвэр) — 2026-10-11** · Хэрэгжүүлэх: v0.2.1 · Холбоотой: PRD-05, ADR-004, [[01_plan_draft]]
> Эх сурвалж: хэрэглэгчийн шийдвэр 2026-10-11 11:32, 11:43
> ⚠️ v0.2.3: хүснэгт `camp_*` → `core_*`, эрхийн код `hr.*` — [[ADR-007_System_Roles_Permissions]]

## 1. Нөхцөл

- Одоо: хэрэглэгчийг зөвхөн CLI (`pilot.ps1 user`)-ээр, имэйлээр; эрх = үндсэн role (OWNER…VIEWER) + кемпийн роль (`camp_user_roles`, кемп бүрээр / бүх кемп).
- Пилот: уурхайн ажилтнуудын олонх нь имэйлгүй байж магадгүй; хэрэглэгч бүр = кемпийн ажилтан.
- Нийгмийн сүлжээ зөвхөн **байгууллага дотор** (ADR-004) → нэг хүн = нэг байгууллага загвар хэвээр хангалттай; байгууллага хоорондын identity хэрэггүй.

## 2. Шийдвэр

### 2.1 Хэрэглэгч = ажилтны бүртгэлээс
- Хэрэглэгчийг **ажилтны картаас** үүсгэнэ (тусдаа "хэрэглэгч бүртгэх" маягт байхгүй). `camp_employees.user_id → core_users.id` (1:1, nullable — нэвтрэх эрхгүй ажилтан байж болно).
- Ажилтны картанд: **утасны дугаар** (заавал, нэвтрэх нэр), **имэйл** (сонголттой).
- Ажлаас гарсан (C-09) / идэвхгүй ажилтан → хэрэглэгч автоматаар идэвхгүй (нэвтрэх эрх тэр даруй — Redis membership cache цэвэрлэнэ).

### 2.2 Нэвтрэх нэр = утасны дугаар (эсвэл имэйл)
- Нэвтрэх хуудас: "Утасны дугаар эсвэл имэйл" + нууц үг.
- **SMS-ээс хамааралгүй загвар:** Supabase Auth-д хэрэглэгч бүр дотоод имэйл хаягтай (имэйлгүй бол `p<утас>@<tenant>.login.invalid` — `.invalid` домэйн RFC 2606-аар хэзээ ч хүргэгддэггүй). Backend `POST /api/v1/auth/resolve-login {identifier}` → утсыг нормчилж (Монгол: 8 оронтой, `+976` хасна) дотоод имэйл рүү хөрвүүлнэ → frontend Supabase-ээр нэвтэрнэ.
  - Шалтгаан: Supabase-ийн утсан нэвтрэлт SMS провайдерын тохиргооноос хамаардаг; `[auth.email] enable_signup`-ийн алдаа (OPS-003) шиг "нэрнээс өөр утгатай" тохиргооны эрсдэлээс зайлсхийнэ. Staging дээр Supabase-ийн native phone+password SMS-гүй ажилладаг нь батлагдвал дараа шилжиж болно.
  - `resolve-login` хэрэглэгч байгаа эсэхийг задруулахгүй (байхгүй ч ижил хариу, rate limit).
  - **Хэрэгжүүлэлт (v0.2.2 Блок 2, D-10):** `resolve-login`-ийн оронд **server-ээр нэвтрүүлэх** `POST /api/v1/auth/sign-in {identifier, password}` → session. Шалтгаан: одоогийн хэрэглэгчид GoTrue-д жинхэнэ имэйлтэй тул утсаар имэйл буцаавал хувийн мэдээлэл задарна. Нууц үг ≥ 12 (D-12, Supabase тохиргоо).

### 2.3 Урилга ба нууц үг — 3 арга (админ сонгоно)
| Арга | Хэзээ | Урсгал |
|---|---|---|
| **Имэйл урилга** | Имэйлтэй ажилтан | "Урилга илгээх" → Gmail SMTP-ээр линк → хэрэглэгч линкээр орж нууц үгээ үүсгэнэ |
| **Урилгын линк** (имэйлгүй) | Утастай ажилтан | Систем нэг удаагийн линк (+QR) үүсгэнэ → админ мессенжер/хэвлэмэлээр өгнө: "Таны нэвтрэх нэр: 9911xxxx. Энэ линкээр орж нууц үгээ үүсгэнэ үү" (хүчинтэй 72 цаг) |
| **Нэг удаагийн нууц үг** | Аль ч | Систем 10 тэмдэгт үүсгэнэ, нэг удаа харуулна → **эхний нэвтрэлт дээр заавал шинэ нууц үг** (`core_users.must_change_password`; backend бусад API-г 403 `PASSWORD_CHANGE_REQUIRED`-аар хаана) |
- "Нууц үг мартсан": имэйлтэй бол имэйл, үгүй бол админаас шинэ линк / нэг удаагийн нууц үг.
- Хэрэглэгч өөрөө нууц үгээ солих (профайл).
- **Session бодлого (v0.2.3 Блок 4 / 4б, PIL-15, 2026-11-07):** (1) **Нууц үг солих** (`/auth/change-password`) — хэрэглэгчийн ӨӨРИЙН access token-оор GoTrue-д солино (`PUT /auth/v1/user`) → **одоогийн төхөөрөмж логинтой үлдэнэ**; GoTrue-ийн бодлогоор бусад төхөөрөмж логоут болно (OPS-013; админ API бүгдийг нь устгадаг тул ашиглахгүй). (2) **Урилга / сэргээлт хүлээн авах** (`/auth/invites/:token/accept`) — бүх session цуцлагдана. (3) **Нэвтэрсэн төхөөрөмжүүд** — хэрэглэгч өөрөө `/account/devices` дээр харж, бусдыг нь гаргана (`GET /auth/sessions`, `DELETE /auth/sessions/:id`, `DELETE /auth/sessions/others`; зөвхөн өөрийн `auth.sessions`, одоогийн төхөөрөмжийг эндээс гаргахгүй). `SessionRevokeService` — `auth.sessions`-ийг системийн холболтоор. (4) Сүүлийн нэвтрэлт — `core_users.last_sign_in_at` (PIL-16).
- **Имэйл илгээх:** Gmail SMTP (app password; Gmail-д 2FA асаалттай байх; өдөрт ~500 хязгаар) — `.env`: `SMTP_HOST/PORT/USER/PASS/FROM`. Supabase Auth-ийн SMTP + имэйлийн загвар 3 хэлээр. Пилотын `site_url` = Funnel хаяг (линк зөв хаяг руу заана).
- Нууц үгийн бодлого: ≥ 10 тэмдэгт (пилотын нэг удаагийн нууц үг 10–16).
- **Хэрэгжүүлэлт (v0.2.2 Блок 3, 2026-10-13 — tech plan D-03, D-04):**
  - **D-03 Урилга = өөрийн токен** (`core_user_invites`: 32 байт, SHA-256 hash, INVITE 72 цаг / RESET 1 цаг, атомаар нэг удаа, хэрэглэгч × зорилгод идэвхтэй ганц). «Линк хуулах» ба «имэйлээр илгээх» нэг токен; `/invite/:token`, `/reset/:token` → backend GoTrue admin API-аар нууц үг тавина. GoTrue-ийн invite-ийг ашиглаагүй шалтгаан: `.invalid` хаягтай хэрэглэгчид ажиллахгүй, `site_url`-аас хамаарна, audit дутуу.
  - **D-04 Имэйл = backend** (`nodemailer`, `.env`: `SMTP_HOST/PORT/USER/PASS/FROM`, `PUBLIC_APP_URL`; 3 хэлний загвар — хэрэглэгчийн `locale`). Supabase Auth-ийн SMTP / загвар **хэрэггүй** болсон; SMTP эсвэл `PUBLIC_APP_URL` алга бол имэйл суваг идэвхгүй (UI-д зөвхөн линк). «Нууц үг мартсан» ч энэ замаар (жинхэнэ имэйлтэй хэрэглэгчид), хариу нь хэрэглэгч байгаа эсэхийг задруулахгүй.
  - «Нэг удаагийн нууц үг» (3 дахь арга) — v0.2.2-ын UI-д гаргаагүй (Q7, Q-B); нөөц нь `pilot.ps1 user`. Нууц үг ≥ 12 (D-12).
  - Хэрэглэгч үүсгэх ганц газар: `UserAdminService` (ажилтны карт + `auth/register`, SEC-005; GoTrue алдаанд rollback).

### 2.4 Эрх: хэрэглэгч дээрх эрх = эцсийн, албан тушаал = загвар
```
Эрхийн каталог (модуль бүрийн permission код)
        │
Албан тушаал ──(загвар: эрхийн багц + хамрах хүрээ)──► [олгох / хэрэгжүүлэх үед ХУУЛНА]
        │                                                        │
Ажилтан.албан тушаал                          Хэрэглэгчийн эрх (user_permissions) ◄── шууд засвар
                                                     = ЭЦСИЙН ЭРХ (guard үүнийг л шалгана)
```
- `user_permissions(tenant, user_id, permission_code, camp_id NULL=бүх кемп, source: TEMPLATE|DIRECT, template_position_id?)` — **ганц эх сурвалж**. Guard зөвхөн үүнийг уншина → зөрчил гарах боломжгүй.
- `position_permission_templates(position_id, permission_code, scope: ALL_CAMPS|EMPLOYEE_CAMP)` — загвар. `EMPLOYEE_CAMP` = ажилтны өөрийн кемп.
- Ажилтанд албан тушаал олгох/солих → загвар хуулагдана (урьдчилж харуулна: нэмэгдэх / хасагдах эрх). Шууд нэмсэн (`DIRECT`) эрх албан тушаал солиход **хадгалагдана**.
- Загвар өөрчлөгдвөл: "Энэ албан тушаалтай N хэрэглэгчид хэрэгжүүлэх?" → урьдчилсан харагдац → батлах (автоматаар биш).
- Хэрэглэгчийн эрхийн дэлгэц: эрх бүрийн дэргэд "загвараас / шууд", загвараас зөрүүтэй бол тэмдэг.
- Бүх өөрчлөлт → өөрчлөлтийн түүх (v0.2.0 audit log).
- **Анхны загварууд:** Кемп админ, Кемп менежер, Катеринг админ (одоогийн 3 роль) + **Ажилтан** (шинэ: Feed пост/сэтгэгдэл, өөрийн засварын хүсэлт/хоолны гомдол, цэс харах).
- **Шилжүүлэлт (migration):** одоогийн `camp_user_roles` → `user_permissions` (`source=TEMPLATE`, роль = загвар) — пилотын эрх өөрчлөгдөхгүй; хуучин хүснэгт уншигдахгүй болсны дараа нэг хувилбар хадгалагдана.
- **Хэрэгжүүлэлт (v0.2.2 Блок 1, 2026-10-12 — tech plan D-02, D-09):** хүснэгт = `camp_user_permissions`; загвар = одоогийн `camp_roles` + `camp_role_permissions` (тусдаа `position_permission_templates` биш — албан тушаал → роль-загвар `camp_position_role_templates`). `camp_user_roles` нь **загвар олгосон бүртгэл** болж үлдэнэ (устгахгүй): олголт нэмэгдэхэд trigger загварыг хуулна, устахад `TEMPLATE` мөр CASCADE. Шилжүүлэлтийн шалгалт: `camp:snapshot --compare a.json b.json --expect=v022-q9`.
- Үндсэн role (OWNER/ADMIN) системийн удирдлагад хэвээр (бүх эрх); бусад role → "Ажилтан" загвар руу.
- **Хэрэгжүүлэлт (v0.2.2 Блок 6б, 2026-10-17 — SEC-009):** хэрэглэгч үүсгэх, урилга, идэвхгүй болгох, ажилтан ↔ хэрэглэгч холбох, роль / шууд эрх олгох, албан тушаалын загвар = **зөвхөн системийн роль OWNER / ADMIN** (модулийн «Кемп админ» биш — `camp.roles.manage`-ээр урилгын токен авч OWNER-ийн нууц үгийг тавих боломжтой байсан). Хэрэглэгчийн шийдвэр: модульд тусдаа эрх удирдах роль байхгүй — бүх роль системийн түвшинд; бүрэн шилжүүлэлт (`core_roles`, `core_permissions`, `hr.*` / `camp.*` / `core.users.*`) — **ADR-007, v0.2.3** (backlog PIL-13).

## 3. Үр дагавар
- (+) Нэг эх сурвалж → "албан тушаал ба хэрэглэгчийн эрх зөрчилдөх" асуудал байхгүй; загвар нь хурдан тохируулах хэрэгсэл л.
- (+) SMS провайдер, төлбөргүй; имэйлгүй ажилтан ч бүртгэгдэнэ.
- (−) Загвар өөрчлөхөд хэрэглэгч рүү автоматаар тархахгүй — зориуд (хяналттай); UI-д "хэрэгжүүлэх" алхам.
- (−) Дотоод `.invalid` имэйл → Supabase-ийн имэйлтэй функц (имэйл урилга) зөвхөн жинхэнэ имэйлтэй хэрэглэгчид.

## 4. Тест (v0.2.1)
Урилгын 3 арга (e2e), эхний нэвтрэлтэд нууц үг солихоос өмнө API 403, утасны нормчлол (unit), `resolve-login` задруулахгүй, эрхийн загвар хуулах/хадгалах/зөрүү, migration (пилотын нөөц дээр staging: өмнөх ба дараах эрх ижил), идэвхгүй ажилтан нэвтэрч чадахгүй.
