# ADR-002 — Пилотын хостинг

> ⛔ **2026-11-11: орлогдсон** → [[ADR-011_Cloud_Hosting]] (пилотын PC 2026-11-18-нд унтрах тул Supabase Cloud + Render + Vercel + R2). Доорх нь түүх.

> 2026-10-19 · Төлөв: **✅ Батлагдсан** · v0.2.4 Блок 0 (Q15, PIL-06, DOC-01)
> Холбоотой: ADR-001 (dedicated deployment), ADR-005 (Cloudflare Tunnel), [[10_v0.2.4_tech_plan]]

## 1. Нөхцөл

- Sino Hydro-ийн Кемп пилот бодит хувийн мэдээлэл ашигладаг.
- Одоогийн тохиргоо нь Windows PC дээрх Supabase CLI, Redis, NestJS болон Caddy; нийтийн урсгал Cloudflare Tunnel-ээр дамжина.
- Нэг машин нь DB, файл, сүлжээ, тэжээлийн нэг цэгийн эвдрэлтэй. Supabase Local CLI нь олон tenant-тай production үйлчилгээний орлуулга биш.
- `StorageService`-ийн interface хэвээр байх тул дараагийн хостинг руу шилжихэд зөвхөн storage adapter солих боломжтой.

## 2. Шийдвэр

v0.2.4-өөс эхлэн пилотыг тусдаа Windows PC дээр үргэлжлүүлнэ. Одоохондоо VPS, Supabase Cloud эсвэл Oracle VM руу шилжүүлэхгүй. Пилотын DB, Supabase API, Redis, backend, Caddy нь loopback-д хязгаарлагдаж, интернэтийн цорын ганц оролт Cloudflare Tunnel байна; Windows Firewall нэмэлт хамгаалалт хэвээр.

Шинэчлэлт бүр staging clone дээр эхэлнэ. Пилотод нэвтрүүлэхийн өмнө шифрлэсэн нөөц, `storage/`-ийн хамт restore, migration, `camp:snapshot` A = B болон health шалгалтыг батална. DB-ийн `postgres` / `supabase_admin` анхдагч нууц үгийг staging-д эхэлж эргүүлж, үр дүнг баталсны дараа пилотод хэрэглэнэ. Нууцууд `.env`-ээс гадуур баримт, git, чатад орохгүй.

## 3. Шилжих нөхцөл

Дараахын аль нэг үүсвэл одоогийн шийдвэрийг дахин үнэлж, шилжилтийн ADR батална:

- Идэвхтэй хэрэглэгч 50 хүрэх, эсвэл нэг dedicated deployment-ийг хоёр ба түүнээс олон байгууллагад зэрэг үйлчлэхээр төлөвлөх.
- PostgreSQL DB + `storage/` нийлбэр 10 GB анхааруулах босгыг давах, эсвэл `pilot.ps1 status`-ийн дискний анхааруулга (<10 GB сул зай эсвэл <10%) давтагдах.
- Гаднын uptime мониторингийн 30 өдрийн хэмжилт 99.5%-иас доошлох, эсвэл цахилгаан, төхөөрөмж, интернэтийн тасалдал үйлчилгээний шаардлагыг хангахгүй болох.
- Өгөгдөл хадгалах байршил, байгууллагын бодлого эсвэл аюулгүй байдлын шаардлага Cloudflare Tunnel / одоогийн PC загварт нийцэхгүй болох.

Эдгээр нь шилжилтийг автоматаар эхлүүлэх босго биш; хэмжилт, эрсдэл, өртгийн харьцуулалтыг хэрэглэгчтэй баталсны дараа шийдвэр гаргана. Тоо ба uptime нь дахин үнэлгээний дохио болохоос SLA амлалт биш.

## 4. Шилжүүлэх тойм

1. Шинэ орчны сүлжээ, өгөгдөл хадгалалт, RLS, нууцын менежмент, мониторинг болон нөөцийн хариуцагчийг тогтооно.
2. Шинэ орчны хоосон DB-г migration-аар үүсгэж, staging backup-аас `public`, Auth өгөгдөл болон `storage/`-ийг сэргээнэ.
3. Migration жагсаалт, tenant/хэрэглэгчийн тоо, эрхийн snapshot A = B, файл hash/уншилт, нэвтрэлт ба health-ийг тулгана.
4. DNS/Tunnel-ийг шилжүүлж, хуучин PC-г rollback хугацаанд унтраалгүй бэлэн хадгална. Шинэ орчин баталгаажсаны дараа хуучин орчныг тусад нь зогсооно.

Шилжилтийн үеэр эх сурвалж DB-д бичилт зөвхөн нэг талд байх ёстой. Хоёр орчинд зэрэг бичүүлэхгүй; rollback шаардлагатай бол хэрэглэгчдэд засварын цонх зарлаж, сүүлчийн баталгаатай нөөцөөс сэргээнэ.
